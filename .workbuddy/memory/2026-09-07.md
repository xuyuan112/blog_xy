### 现象
用户的博客项目（前端 frontend-firefly + 后端 blog-web-app）接入网易云歌单 ID `17688490382` 后，
明明歌单里有 14 首歌，播放器只显示 5 首。其中一些非 VIP 歌曲也被错误地当作"不可播"过滤掉了。

### 根因（已定位并修复）
后端 `NetEaseMusicService.fetchAndFilterPlaylist()` 有 3 个串联问题：

1. **无节流并发探测** —— 14 首歌一次性 `CompletableFuture.supplyAsync` 并发打
   `music.163.com/song/media/outer/url`，网易云对未登录 IP 会触发限流 / 偶发非预期响应。
2. **探测失败 = 永久负缓存** —— `if (url == null)` 一律写
   `blog:site:music:bad:{id}=1`，TTL 10 分钟，把网络抖动和真 VIP 不可播混为一谈。
3. **playlist 结果再次缓存 10 分钟** —— 即便探测逻辑后面修好，错误结果仍然被缓存复用。

### 修复
文件：`blog-parent/blog-web/blog-web-app/src/main/java/com/xuyuan/blog/web/service/music/NetEaseMusicService.java`

- `getPlaylist()` 下调下游改名为 `fetchPlaylistAll()`；缓存时长从 10 min → 5 min
- `fetchPlaylistAll()` 不再做预过滤，只补齐 metadata（top10 用 `tracks`、剩 4 首走 `song/detail` 补全），
  按 `trackIds` 顺序输出 14 首
- `resolveAudioUrl()` 加 `Semaphore(PROBE_MAX_CONCURRENCY=3)` 探测并发闸门；
  用三态 `ProbeResult.{OK, VIP_OR_INVALID, NETWORK_ERROR}` 区分
- `probeOuterUrl()` 返回 `ProbeOutcome(result, url)`：5xx/429/IOException 走 NETWORK_ERROR（不缓存，让重试），
  非音频 content-type 或 < 100KB 占位才走 VIP_OR_INVALID（30 分钟负缓存）

## 修复移动端图片加载失败（文章/说说/相册）

### 根因
图片 URL 是后端 `FileServiceImpl.url()` 写入数据库的 MinIO 内网地址
`http://192.168.10.103:9000/blog/{scene}/{uuid}.png`。开发机通过 192.168.10.x 网卡能访问
MinIO，但手机等跨网段设备访问不到该内网地址 → 图片全部加载失败。

### 方案：后端 MinIO 同源代理 + 前端转相对路径 + dev proxy
1. 后端新增 `blog-web-app/.../controller/file/SiteFileController.java`
   - `GET /xuyuan/file/**`（用 `HttpServletRequest.getRequestURI()` 手动解析，**不要用
     `{*path}` 语法——Spring Boot 3.0.5 下 `{*path}` 路由不匹配返回空 404**）
   - 解析出 {bucket}/{object}，校验 bucket 必须是 minioConfig.getBucket()，再流式转发 MinIO
   - 加 `@ConditionalOnProperty(minio.enabled=true)` 防止 minio 未启用时注入失败
2. 前端新增 `src/utils/file-url.ts` 的 `resolveFileUrl(url)`
   - 私有网段绝对地址（10.x / 172.16-31.x / 192.168.x / localhost）→ 转 `/xuyuan/file{pathname}`
   - 相对路径 / data: / blob: / 外网 URL 原样返回
3. `astro.config.mjs`：vite.server.proxy 加 `/xuyuan` → `http://localhost:8081`（图片走后端代理）
4. 图片渲染点接入 resolveFileUrl：
   - 文章/杂谈详情封面 + 正文 markdown 图片（sanitizeHtml transformTags img）
   - 文章列表 ArticleFeed.svelte、说说 DynamicFeed/DynamicSidebar（images 映射）
   - 相册 index/[album]/photo/[id] + AlbumCard

### 验证
- 后端 `GET /xuyuan/file/blog/article/xxx.png` → 200 image/png；非法 bucket/缺失对象 → 404
- 前端 dev proxy `127.0.0.1:4321/xuyuan/file/...` → 200 image/png
- 文章详情页封面 src 已渲染为 `/xuyuan/file/blog/article/...`（相对路径）
- 相册封面 src 已渲染为 `/xuyuan/file/blog/gallery/...`

### 部署注意
- 生产部署（Nginx 反代）时需把 `/xuyuan` 反向代理到后端 8081，前端相对路径图片才可用；

## 修复"说说的评论一直显示评论失败"bug

### 根因
上一轮 `dynamic-inline-comments.ts` 里用了 Svelte 4 风格的挂载代码：
```ts
this.commentInstance = new BackendComments({ target: panel, props: {...} });
```
但当前项目用的是 **Svelte 5**（v5.57.0），编译器把 `.svelte` 文件编译为：
```js
export default function BackendComments($$anchor, $$props) { ... }
```
是一个**函数**，不是 class。`new BackendComments(...)` 直接抛 `BackendComments is not a constructor`，
于是 catch 里 fallback 渲染 `<p class="dynamic-comment-error">评论加载失败，请稍后重试</p>`。

### 修复（`npx astro check` 0 error）
Svelte 5 的客户端 API 必须用：
- `mount(Component, { target, props })` 返回组件 exports
- `unmount(componentInstance)` 销毁

另外 Svelte 5 中 props 在 mount 调用时锁定、不是响应式的；要更新必须重 mount。所以：
- 每次打开折叠 → 都没有现成 instance → mount 新的
- 关闭折叠 / disconnectedCallback → unmount 销毁
- targetType 在 dataset 是 `number`，BackendComments 期望 `1 | 2`，用 `as 1 | 2` 断言

`dynamic-inline-comments.ts` 重写：使用 `await import("svelte")` 取得 `mount/unmount`，
`await import("@/components/comment/BackendComments.svelte")` 取得组件。

另外多加：
- 加载时给一个 `<p class="dynamic-comment-loading">正在加载评论...</p>` 占位，svelte 模块动态 import
  需要时间，避免用户以为没反应
- styles/dynamic.css 增加 `.dynamic-comment-loading` 样式

### 验证
- `npx astro check` 0 error 0 warning
- `/src/components/pages/dynamic/dynamic-inline-comments.ts` 模块 dev server 200
- `/dynamic/` 页面 200

### 关键认知
- **Svelte 5 客户端不能用 `new Component(...)`**；必须 `import { mount, unmount } from 'svelte'`
- Svelte 5 的 `mount` 返回值是组件的 exports（默认 `{}`），不是 instance，调用方需要保存好以便后续 unmount
- `props` 在 mount 调用时锁定；要做响应式 props 更新用 `createSlice` / `bind:value` 内部 reactive，
  或直接在外部 unmount + mount
